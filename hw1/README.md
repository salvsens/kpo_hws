# «ВышКат» — учёт парка кикшеринга

ДЗ №1 по КПО: SOLID, DI-контейнер, юнит-тесты. Консольное приложение на Go,
в котором оператор принимает транспорт после техосмотра, ставит на баланс
вещи и получает отчёты по парку.

- Спецификация (что делает приложение, команды, сценарии) — [`docs/spec.md`](docs/spec.md).
- Архитектурные решения — [`docs/adr/`](docs/adr/), ADR-0001…0005.
- Журнал использования ИИ — [`AI_USAGE.md`](AI_USAGE.md).

## Запуск

Требуется Go 1.26 и [golangci-lint v2](https://golangci-lint.run/docs/welcome/install/)
(нужен только для `make lint` и `make check`).

```bash
make run      # запустить REPL
make test     # тесты
make cover    # тесты + отчёт о покрытии
make check    # fmt + vet + lint + test — прогоняется перед каждым коммитом
make help     # все команды
```

Все сценарии из спецификации показывает команда `demo`:

```bash
printf 'demo\nexit\n' | make run
```

Команды REPL:

| Команда | Что делает |
|---|---|
| `add-vehicle <вид> <название> <простота> [кВт·ч]` | техосмотр и приём транспорта; вид: `scooter`, `bike`, `ebike` |
| `add-item <вид> <название> [кВт·ч]` | постановка вещи на баланс; вид: `helmet`, `dock`, `cabinet` |
| `report` | число единиц (всего / транспорт / вещи) и суточное энергопотребление |
| `beginners` | транспорт, который можно выдавать новичкам |
| `inventory` | все объекты на балансе: инвентарный номер, вид, название |
| `demo`, `help`, `exit` | демонстрация, справка, выход |

Пример:

```
> add-vehicle scooter Ninebot-Max 7 0.4
Техосмотр пройден. Принят: Ninebot-Max, инв. № VK-SC-0001
> add-vehicle ebike Old-Volt 6 3.5
Ошибка: транспорт не прошёл техосмотр: суточный расход 3.50 кВт·ч больше лимита 2.00 кВт·ч — проверьте батарею → транспорт не принят; устраните причину и повторите приёмку
> add-item cabinet Шкаф-12 1.5
На баланс поставлен: Шкаф-12, инв. № VK-CC-0001
> report
Всего: 2 (транспорт: 1, вещи: 1)
Суточное энергопотребление: 1.90 кВт·ч
```

## Структура

```
cmd/vyshkat/      точка входа: контейнер dig и запуск REPL
internal/domain/  предметная область: Asset, Vehicle, EnergyConsumer, Kind и шесть типов
internal/fleet/   сервисный слой: Fleet, ServiceCenter, BeginnerPolicy, отчёт
internal/cli/     REPL: разбор команд, таблица видов, вывод, demo
docs/             спецификация и ADR
```

Зависимости направлены в одну сторону: `cmd/vyshkat → cli → fleet → domain`
(ADR-0002). `domain` не импортирует других пакетов проекта, `dig` импортирует
только `cmd/vyshkat`.

## Логика решений

### Доменная модель (ADR-0001, ADR-0004)

Отправная точка — таблица свойств из спецификации:

| Объект | Инв. номер | Энергия | Простота | Транспорт |
|---|:-:|:-:|:-:|:-:|
| Электросамокат, электровелосипед | ✓ | ✓ | ✓ | ✓ |
| Велосипед | ✓ | — | ✓ | ✓ |
| Шлем | ✓ | — | — | — |
| Док-станция, зарядный шкаф | ✓ | ✓ | — | — |

Свойства пересекаются, но не вкладываются друг в друга: велосипед — транспорт
без энергии, зарядный шкаф — потребитель энергии, но не транспорт. Поэтому
вместо одной иерархии — три маленьких интерфейса в `internal/domain`:

```go
type Asset interface {          // объект на балансе
    Kind() Kind
    ID() string
    Name() string
}
type Vehicle interface {        // прокатный транспорт; любой транспорт стоит на балансе
    Asset
    BeginnerSimplicity() int
}
type EnergyConsumer interface { // потребитель энергии; намеренно не встраивает Asset
    DailyEnergyKWh() float64
}
```

Общий код — во встраиваемых неэкспортируемых структурах `baseAsset`,
`baseVehicle`, `energyUsage`. Конкретный тип собирается из нужных частей:
`Bicycle` = `baseVehicle`, `ChargingCabinet` = `baseAsset` + `energyUsage`.
Объект создаётся только конструктором `NewXxx`, который проверяет инварианты
(номер и название не пустые, простота 1–10, расход > 0) и возвращает
sentinel-ошибку из `domain/errors.go`. Строки `var _ EnergyConsumer = (*ChargingCabinet)(nil)`
проверяют реализацию интерфейсов при компиляции.

Вид объекта (`Kind{Code: "SC", Title: "электросамокат"}`) хранится в самом
объекте: из него берутся префикс номера и название для инвентарного списка.

### Парк, техосмотр, правило для новичков (ADR-0004, ADR-0005)

- `fleet.Fleet` хранит объекты в срезе — порядок постановки сохраняется (FR-8).
- **Номера без пропусков.** `NextID(kind)` показывает следующий свободный номер,
  не занимая его; счётчик вида растёт только после успешной постановки. Если
  транспорт не прошёл техосмотр, следующий получит тот же номер.
- **Техосмотр** — интерфейс `ServiceCenter` с методом `Inspect(v) Verdict`.
  Отказ — нормальный результат проверки, поэтому `Verdict{Accepted, Reason}`,
  а не `error`. Для парка отказ уже ошибка операции: `AddVehicle` возвращает
  `ErrInspectionRejected` с причиной. Реализация по умолчанию —
  `EnergyLimitInspection`: отказ при расходе больше 2.0 кВт·ч; транспорт без
  энергии (велосипед) проходит.
- **Правило для новичков** — интерфейс `BeginnerPolicy`, по умолчанию
  `MinSimplicityPolicy{Min: 6}`. Порога `>= 6` в коде парка нет.
- **Защита учёта.** `AddItem` не принимает транспорт (`ErrVehicleAsItem`) —
  иначе его можно было бы поставить на баланс в обход техосмотра. Объект с
  номером, который парк не выдавал, не принимается (`ErrUnexpectedID`).
- `Fleet` возвращает данные (`Report`, `[]domain.Vehicle`, `[]domain.Asset`),
  форматирует их консоль.

### Консоль (`internal/cli`)

- `REPL.Run(in io.Reader, out io.Writer)` — ввод-вывод приходит снаружи,
  поэтому REPL тестируется через `strings.Reader` и `bytes.Buffer`.
- Слова консоли (`scooter`, `helmet`…) сопоставлены видам и конструкторам
  в таблицах `vehicleSpecs` и `itemSpecs` (`cli/kinds.go`), а не в `switch`.
- Ошибки выводятся по схеме «что произошло → что делать»: подсказка
  выбирается через `errors.Is` по таблице `hints` (`cli/errors.go`).
- `demo` — список строк-команд, которые выполняет тот же `dispatch`, что и
  ввод оператора: демонстрация проверяет настоящие команды.

### DI-контейнер (ADR-0003)

`cmd/vyshkat/main.go` регистрирует в `go.uber.org/dig` четыре конструктора
(`newServiceCenter`, `newBeginnerPolicy`, `fleet.New`, `cli.New`) и запрашивает
`*cli.REPL`. Контейнер сам строит граф и порядок вызовов. Провайдеры техосмотра
и правила возвращают интерфейсы: `dig` связывает зависимости по точному типу.
Остальные пакеты о контейнере не знают и получают зависимости через параметры
конструкторов, поэтому в тестах фейк передаётся напрямую, без контейнера.

## SOLID

**S — единственная ответственность.** Каждый пакет и тип меняется по одной причине:
`domain` — данные и инварианты, `fleet.Fleet` — учёт и номера,
`EnergyLimitInspection` — только решение техосмотра, `MinSimplicityPolicy` —
только правило для новичков, `cli` — ввод-вывод. `Fleet.Report()` возвращает
структуру `Report`, а не текст: формат вывода меняется в `cli/reports.go`,
не затрагивая парк.

**O — открытость для расширения.** Новый вид транспорта — новый тип в `domain`
и одна запись в `cli.vehicleSpecs`; `Fleet`, отчёты и техосмотр не меняются.
Вид — метод `Kind()` у объекта, а не `switch v.(type)` в парке: новый тип
без вида не скомпилируется. Новое правило техосмотра или отбора новичков —
новая реализация `ServiceCenter`/`BeginnerPolicy` и одна строка в `main.go`.

**L — подстановка Лисков.** Любой `domain.Vehicle` одинаково проходит
`Fleet.AddVehicle` и `ServiceCenter.Inspect`, любой `domain.Asset` —
`Fleet.Inventory`. Подтипы не ослабляют контракт: велосипед не реализует
`EnergyConsumer`, а не возвращает «заглушку» 0 кВт·ч; шлем не обязан иметь
бессмысленную простоту. Фейки в тестах подставляются вместо настоящих
реализаций без изменения кода парка.

**I — разделение интерфейсов.** Интерфейсы по 1–3 метода. `EnergyConsumer`
содержит только `DailyEnergyKWh()` и не встраивает `Asset`: расчёту энергии
не нужны номер и название. `ServiceCenter` и `BeginnerPolicy` — по одному
методу, поэтому фейк в тесте занимает 5 строк.

**D — инверсия зависимостей.** `Fleet` зависит от абстракций `ServiceCenter`
и `BeginnerPolicy`, объявленных на стороне потребителя (в пакете `fleet`), и
получает их в конструкторе `fleet.New`. Конкретные реализации выбирает только
`cmd/vyshkat` через контейнер.

## Ответы на обязательные вопросы

### Какой принцип SOLID применён наиболее явно и где?

**ISP** — в `internal/domain`. Таблица свойств показала, что «транспорт»
и «потребитель энергии» пересекаются, но не вкладываются друг в друга, поэтому
`Asset`, `Vehicle` и `EnergyConsumer` — отдельные интерфейсы
(`domain/asset.go`, `domain/vehicle.go`, `domain/energy.go`). `EnergyConsumer`
намеренно не встраивает `Asset`. Результат: `Bicycle` реализует только
`Vehicle`, `ChargingCabinet` — `Asset` и `EnergyConsumer`, и ни один тип не
реализует метод, который ему не нужен. `TestCapabilities` (`domain/domain_test.go`)
фиксирует эту таблицу для всех шести видов.

### Какой принцип сознательно ограничен или «почти нарушен» и почему это приемлемо?

1. **SRP в `domain.Kind`.** Поле `Title` («электросамокат») — это текст для
   вывода, то есть забота консоли, а живёт оно в домене (`domain/kind.go`).
   Приемлемо: интерфейс один (консоль), а альтернатива — `switch` по типам
   в `fleet` или `cli` — ломала бы OCP. Если появится второй интерфейс
   (HTTP, другой язык), названия переедут в слой представления, коды останутся.
2. **ISP/YAGNI для простоты.** `BeginnerSimplicity()` — метод `Vehicle`,
   а не отдельный интерфейс `BeginnerFriendly`: все носители простоты —
   транспорт. Если появится прокатный не-транспорт, интерфейс выделяется
   без правки остального кода (ADR-0001).
3. **DIP в консоли.** `cli.REPL` зависит от конкретного `*fleet.Fleet`, а не
   от интерфейса. У парка одна реализация, а в тестах консоли используется
   настоящий `Fleet` с подменённым техосмотром — интерфейс был бы
   «декоративным».
4. **OCP в консоли.** Новый вид всё же требует одной записи в
   `cli/kinds.go` и строки в справке: слова консоли — часть интерфейса
   пользователя, их приходится перечислить где-то явно.

### Что сломается (или не сломается) при расширении?

- **Новый вид транспорта (моноколесо).** Добавляются тип `Monowheel` из
  `baseVehicle` + `energyUsage` с конструктором (~15 строк), значение
  `KindMonowheel` и одна запись в `cli.vehicleSpecs`. `Fleet`, `Report`,
  `Beginners`, техосмотр, нумерация и существующие тесты не меняются.
  Если забыть вид, проект не соберётся: `Kind()` входит в `Asset`.
- **Сотрудники.** По ТЗ они не ставятся на баланс, значит, не реализуют
  `Asset` и в парк не попадают. Это новый пакет рядом с `fleet` (например,
  `internal/staff`); существующий код не меняется. Если сотруднику понадобится
  выдавать транспорт, новый сервис будет зависеть от `fleet.Fleet`, а не
  наоборот.
- **Склад запчастей.** Запчасти учитываются количеством, а не поштучно, поэтому
  это отдельный пакет со своей моделью. Если какие-то запчасти ставятся на
  баланс поштучно, они реализуют `Asset` с новым `Kind` — `Fleet` их примет
  через `AddItem`, отчёт посчитает их вещами. Ограничение, которое
  сломается при росте: формат номера `%04d` рассчитан на 9999 объектов
  одного вида.
- **Новое правило техосмотра или «для новичков»** (например, «простота ≥ 6
  и расход ≤ 1 кВт·ч»): новая реализация интерфейса и замена одного
  провайдера в `cmd/vyshkat/main.go`.

### Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется зависимость?

| Тест | Что фиксирует |
|---|---|
| `TestAddVehicleUsesServiceCenter` (`fleet/fleet_test.go`) | Парк выполняет решение техосмотра: приём и отказ, причина отказа доходит до вызывающего кода, техосмотр вызван ровно один раз, отказ не расходует номер |
| `TestAddVehicleChecksIDBeforeInspection`, `TestAddItem` | Техосмотр **не** вызывается для чужого номера и для вещей; транспорт нельзя провести через `AddItem` |
| `TestEnergyLimitInspection` (`fleet/rules_test.go`) | Правило по умолчанию: 2.0 кВт·ч проходит, 2.01 — отказ с причиной, велосипед проходит |
| `TestMinSimplicityPolicy` (`fleet/rules_test.go`) | Граница правила для новичков: 1 и 5 — нет, 6 и 10 — да |
| `TestReportsAndLists` (`fleet/fleet_test.go`) | `Beginners()` слушается подменённого правила `allowByName`, а не зашитого порога |
| `TestCommands`, `TestDemo` (`cli/cli_test.go`) | Отказ техосмотра и граница 6 в выводе консоли |
| `TestBuildContainer` (`cmd/vyshkat/main_test.go`) | Граф `dig` собирается, техосмотр по умолчанию — `EnergyLimitInspection` |

**Подмена.** `fleet.New(sc ServiceCenter, policy BeginnerPolicy)` принимает
зависимости через конструктор. В тесте вместо `EnergyLimitInspection`
передаётся фейк:

```go
type fakeServiceCenter struct {
    verdict   fleet.Verdict // какое решение вернуть
    inspected []string      // кого проверяли — для проверки вызовов
}

sc := &fakeServiceCenter{verdict: reject}
f := fleet.New(sc, defaultPolicy)
```

Это spy: возвращает заданное решение и запоминает вызовы. В тестах консоли —
stub `stubServiceCenter`, который только отвечает. Контейнер в тестах не
нужен: он только собирает граф в `main`.

Покрытие (`make cover`): `domain` и `fleet` — 100%, `cli` — 97.7%, всего — 95%.
