# 0001. Доменная модель: малые интерфейсы и встраивание структур

Дата: 2026-10-25

## Статус

Принято

## Контекст

На баланс «ВышКат» ставятся транспорт и вещи (спецификация, раздел 3).
Свойства объектов пересекаются, но не совпадают:

- инвентарный номер есть у всех;
- энергию потребляют электротранспорт, док-станция и зарядный шкаф;
  велосипед — транспорт без энергии, зарядный шкаф — потребитель энергии,
  но не транспорт;
- «простота для новичка» имеет смысл только для транспорта: она оценивает
  управление, а у шлема и шкафа управления нет.

ТЗ требует абстракции для потребителей энергии и для инвентаризируемых
объектов, а также расширение видов транспорта без массовой правки кода.
В Go нет наследования: общее поведение задаётся интерфейсами, общий код —
встраиванием структур.

## Решение

Пакет `internal/domain`, три интерфейса:

```go
type Asset interface {          // объект на балансе
    ID() string
    Name() string
}

type Vehicle interface {        // прокатный транспорт
    Asset
    BeginnerSimplicity() int
}

type EnergyConsumer interface { // потребитель энергии
    DailyEnergyKWh() float64
}
```

- `Vehicle` встраивает `Asset`: по ТЗ любой транспорт стоит на балансе.
- `EnergyConsumer` **не** встраивает `Asset` (ISP): расчёту суммарной
  энергии нужен только расход. Принадлежность к потребителям проверяется
  через type assertion `a.(EnergyConsumer)`.
- Простота — метод `Vehicle`, а не отдельный интерфейс: все её носители —
  транспорт.

Общий код — в неэкспортируемых встраиваемых структурах:

| Структура     | Поля               | Методы                   |
|---------------|--------------------|--------------------------|
| `baseAsset`   | `id`, `name`       | `ID()`, `Name()`         |
| `baseVehicle` | `baseAsset`, простота | `BeginnerSimplicity()` |
| `energyUsage` | суточный расход    | `DailyEnergyKWh()`       |

Конкретные типы собираются из этих частей:

| Тип               | Встраивает                     | Реализует                 |
|-------------------|--------------------------------|---------------------------|
| `Bicycle`         | `baseVehicle`                  | `Vehicle`                 |
| `ElectricScooter` | `baseVehicle`, `energyUsage`   | `Vehicle`, `EnergyConsumer` |
| `ElectricBike`    | `baseVehicle`, `energyUsage`   | `Vehicle`, `EnergyConsumer` |
| `Helmet`          | `baseAsset`                    | `Asset`                   |
| `DockStation`     | `baseAsset`, `energyUsage`     | `Asset`, `EnergyConsumer` |
| `ChargingCabinet` | `baseAsset`, `energyUsage`     | `Asset`, `EnergyConsumer` |

Инварианты:

- объект создаётся только конструктором `NewXxx`, который возвращает
  `(*Xxx, error)`; встраиваемые структуры не экспортированы, поэтому обойти
  конструктор снаружи пакета нельзя;
- номер и название не пустые; простота от 1 до 10; суточный расход больше 0;
- нарушение — sentinel-ошибка (`ErrInvalidAsset`, `ErrInvalidSimplicity`,
  `ErrInvalidEnergy`), обёрнутая через `%w`; проверка — `errors.Is`;
- соответствие типов интерфейсам проверяется при компиляции:
  `var _ EnergyConsumer = (*ChargingCabinet)(nil)`. Это важно для
  `EnergyConsumer`: опечатка в имени метода иначе молча исключит объект
  из суммы энергии.

Чего в домене нет намеренно:

- порога «простота ≥ 6»: это бизнес-правило, а не инвариант данных; оно
  живёт в сервисном слое и заменяется без правки домена (FR-7);
- генерации инвентарных номеров: номер приходит в конструктор готовым,
  выдаёт его сервис парка (FR-5).

## Альтернативы

- Один интерфейс `Device` со всеми методами — отклонён: велосипед и шлем
  были бы вынуждены реализовать `DailyEnergyKWh()` и возвращать 0, а шлем —
  ещё и бессмысленную простоту (нарушение ISP и LSP).
- `EnergyConsumer` встраивает `Asset` — отклонён: расчёт энергии зависел бы
  от методов, которыми не пользуется; фейк в тестах усложнился бы.
- Отдельный интерфейс `BeginnerFriendly` — отклонён как преждевременный:
  все носители простоты — транспорт. Если появится прокатный не-транспорт,
  интерфейс выделяется без правки остального кода.
- Экспортируемые поля без конструкторов — отклонены: можно создать объект
  с простотой 15 или отрицательным расходом.

## Последствия

- Плюсы: новый вид транспорта — новый тип из готовых частей и конструктор
  (≈15 строк), без правки существующих типов (OCP). Таблица свойств из
  спецификации один в один видна в коде.
- Минусы/риски: конструкторы электрических типов похожи друг на друга;
  общая часть вынесена в `newElectricVehicle`/`newElectricItem`, но
  остаточное дублирование есть.
- Открыто: для инвентарного списка (FR-8) и префикса номера (FR-5) нужен
  вид объекта («электросамокат», `SC`). Сейчас в домене его нет — решить
  при реализации сервиса парка: метод у типа или сопоставление снаружи.
  Решено в ADR-0004: метод `Kind()` у `Asset`.
